1. Requerimiento del cliente

Optimización del cálculo de prenómina para retiros Se ha identificado que el sistema presenta un rendimiento deficiente al calcular los conceptos correspondientes a un empleado durante el proceso de recálculo de la prenómina, especialmente al cargar más de 500 retiros. Este retraso puede superar las 10 horas, afectando la eficiencia del proceso de nómina. Criterios de aceptación: 1. El tiempo de cálculo para más de 500 retiros no debe exceder los 30 minutos. 2. El proceso de recálculo debe completarse sin errores en todos los escenarios de prueba. 3. El rendimiento del sistema debe ser medido y documentado antes y después de la optimización.

2. Análisis del coordinador

Requerimiento centrado en rendimiento del recálculo post-retiro masivo en prenómina. El síntoma (10+ horas con 500+ retiros) apunta a un cuello de botella compuesto: (a) orquestación frontend empleado a empleado vía HTTP, y (b) motor SQL de liquidación por concepto, con ramas específicas de retiro (NEMPFD_RUN, NEVED, funciones *_RET). El retiro masivo en sí (FRT_NEMP) parece ser una sola llamada; el problema crítico ocurre en el recálculo posterior disparado por closeRemoMassiveNEMP. Se evalúan dos líneas de solución: OPCIÓN 1 — Proceso asíncrono (patrón RIPS JSON / COESME509) Trabajar como la generación de RIPS JSON: encolar el recálculo masivo post-retiro, liberar la UI y permitir que el usuario siga operando mientras el job corre en segundo plano con polling de estado. OPCIÓN 2 — Optimización SQL set-based (batch en servidor) Dejar de invocar PRENOMINA empleado a empleado. Crear un procedimiento que calcule/sume provisiones y conceptos de retiro para el lote completo y persista el resultado con UPDATE/merge masivo sobre NEMPFD (y tablas auxiliares NEMPFD_RUN / NEVED según aplique). RECOMENDACIÓN DEL COORDINADOR: Implementar ambas en fases complementarias — Opción 2 como núcleo para cumplir la meta de 30 minutos; Opción 1 como capa de experiencia de usuario para no bloquear la pantalla de prenómina durante el proceso.

Resumen ejecutivo

El recálculo de prenómina tras retiros masivos NO es un proceso batch. Tras procesar retiros con FRT_NEMP.RETIRAR_EMPLEADOS, el frontend invoca AddConXCar() que ejecuta un loop secuencial (for + await) llamando ADDEL_CONCEPTOS_DE_CARGOS_NUMDOC.PRENOMINA una vez por empleado. Con 500 retiros ≈ 500 round-trips HTTP + 500 ejecuciones completas del motor de conceptos en SQL Server (incluyendo ramas de retiro documentadas: FNK_VALORCONCEPTO_NEMPFD_RUN_RET, FNK_VALOR_CONCEP_RETIRO_RUN, SPK_CALCULAR_RETIROS, tabla NEMPFD_RUN filtrada por HOST_NAME()). Estimación orientativa: 10 h / 500 empleados ≈ 72 s por empleado (red + SQL). Meta: 30 min / 500 ≈ 3,6 s por empleado → se requiere reducción ~20× mediante batch en backend, optimización de SP/funciones y ajustes menores en frontend (eliminar latencias artificiales, posible paralelismo acotado). No se requiere necesariamente cambio de esquema de tablas; sí optimización de procedimientos, índices y un nuevo endpoint batch. El código fuente del backend (qrystalos.server) no está disponible en este workspace — el desarrollador debe confirmar la ruta y revisar SPK_ADDDEL_CONCEPTOS_DE_CARGOS_NUMDOC / capa MODELO ADDDEL_CONCEPTOS_DE_CARGOS_NUMDOC.

4. Cambios propuestos

Fase A — Opción 2: SQL batch (prioridad para cumplir SLA)

4.A.1 SQL Server — SP set-based de recálculo post-retiro

Crear SPK_PRENOMINA_RECALCULO_RETIROS_BATCH (nombre sugerido) que reemplace N invocaciones unitarias a SPK_ADDDEL_CONCEPTOS_DE_CARGOS_NUMDOC:

  1. Entrada: @CNSPAGO, @CNS_RPDX (lote de retiros) o tabla @NUMDOCS.
  2. Paso 1 — Staging: Cargar empleados a recalcular desde RPDX / lista en tabla temporal #EMP_RETIRO.
  3. Paso 2 — Cálculo set-based: Invocar lógica de provisiones/conceptos de retiro en bloque (reutilizar o refactorizar FNK_VALORCONCEPTO_NEMPFD_RUN_RET, SPK_CALCULAR_RETIROS, NEVED). Objetivo del coordinador: sumar provisiones del lote antes de persistir, no iterar concepto×empleado desde el cliente.
  4. Paso 3 — Persistencia masiva:
    • DELETE conceptos previos del período para NUMDOC del lote (equivalente PROCESO=DEL filtrado).
    • INSERT o MERGE en NEMPFD desde resultado calculado (#RESULTADO_CONCEPTOS).
    • Actualizar totales en NEMPF si el flujo actual lo hace al final de PRENOMINA unitario.
  5. Paso 4 — Salida: OK/KO, cantidad procesada, tabla de errores por NUMDOC.
  6. Validación obligatoria: comparar salida del SP batch vs PRENOMINA unitario en muestra de 20 empleados (diff = 0 en VALOR por CODCONCEPTO).

4.A.2 Backend

  1. Nuevo método ADDDEL_CONCEPTOS_DE_CARGOS_NUMDOC.PRENOMINA_RETIROS_BATCH (o MODELO dedicado NOM_PRENOMINA) que invoque el SP.
  2. Confirmar ruta de qrystalos.server (null en config actual).

4.A.3 Frontend

  1. En closeRemoMassiveNEMP: reemplazar processEmploye → AddConXCar por una sola llamada al endpoint batch con CNSPAGO + lista/CNS RPDX.
  2. Mantener AddConXCar secuencial solo para recálculo unitario (botón por fila / un empleado).
  3. Eliminar setTimeout(..., 200) del loop en procesos masivos.

Fase B — Opción 1: Async job (UX, reutilizar patrón RIPS)

4.B.1 Composable nuevo

Crear src/composables/useNomi/usePrenominaRetirosAsync.js basado en useProcesoAsyncJob.js (mismo patrón que useRipsJsonAsync.js y useCierrePeriodoAsync.js):

  • INICIAR_RECALCULO_RETIROS_JOB → retorna CNS del job.
  • EJECUTAR_RECALCULO_RETIROS_ASYNC → fire-and-forget; internamente ejecuta SP batch de Fase A.
  • PROCESO_JOB.CONSULTAR_ESTADO_JOB → polling cada 15 s, max ~60 min.

4.B.2 PreNominaComponent.vue

  1. Tras RETIRAR_EMPLEADOS, encolar job async en lugar de bloquear con modal showPrenomProgress hasta terminar.
  2. Mostrar banner/toast no bloqueante: "Recálculo de retiros en curso — puede continuar trabajando".
  3. Indicador de progreso opcional en toolbar (ESTADO, % si el job lo reporta).
  4. Al completar: notificación + refresco de tabla NEMPF; si ERROR, listar NUMDOC fallidos.
  5. Bloqueo de concurrencia: deshabilitar nuevo recálculo del mismo CNSPAGO mientras job ESTADO = PENDIENTE/EJECUTANDO.

4.B.3 Backend / SQL

  1. Reutilizar infraestructura COESME509 / tabla PROCESO_JOB (ya usada por RIPS y cierre contable).
  2. El job async debe registrar TIEMPO_TRANSCURRIDO para documentación antes/después (requisito cliente #3).

No obligatorio para Fase A (tablas temporales en SP). Fase B reutiliza PROCESO_JOB existente. Opcional: NOM_PERF_LOG para auditoría de duración.

5. Qué tener en cuenta

  • Regresión funcional: Los conceptos de retiro tienen reglas distintas (NEVED, *_RET). Validar que valores calculados batch = valores calculados empleado a empleado en muestra de 10–20 casos.
  • Concurrencia (Opción 1): Usuario editando novedades del mismo CNSPAGO mientras corre job async — bloquear o advertir. Dos jobs simultáneos sobre mismo período deben rechazarse.
  • Equivalencia funcional (Opción 2): El SP batch debe reproducir exactamente la lógica de retiro (NEVED, *_RET); no simplificar provisiones sin validación contable/nómina.
  • Timeout: Con Opción 1 async, el HTTP de ejecución es fire-and-forget — evita timeout de gateway. El SP batch puede correr el tiempo necesario dentro del job (hasta 60 min polling).
  • Memoria SQL: Batch masivo puede aumentar tempdb; probar en copia con datos reales del cliente.
  • Permisos: USGRUH MENUQ_NOMINA / Prenomina — sin cambio esperado.
  • Variable USVGS NUEVA_VISTA_RETIROS: Hay dos flujos de retiro (clásico txt vs vista nueva); probar ambos.
  • Ambientes: develop → calidad con dataset de 500+ retiros en preversión antes de producción.
  • Documentación de resultados: Adjuntar tabla antes/después al dictamen o ticket (requisito explícito del cliente).
