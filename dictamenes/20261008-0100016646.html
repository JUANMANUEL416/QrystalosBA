1. Requerimiento del cliente

Error al validar nota de débito ante el ministerio (FEV-RIPS / SISPRO). Consecutivo reportado: 01D00020869. Pasos del usuario: acceder a notas de débito, seleccionar la nota e intentar validar. Contexto operativo: el error solo ocurre cuando se abre el flujo desde la ventana de Proceso DIAN (NotiDian); desde Cartera · Notas DB/CR el mismo consecutivo valida correctamente.

2. Análisis del coordinador

Paso 0 — ¿Ya existe? Defecto de integración frontend, no capacitación ni funcionalidad nueva. El control «Validar Ahora» en Envíos y Respuestas · FEV RIPS está implementado para notas (help Notas DB/CR) y para documentos en Proceso DIAN (permiso NOTIDIAN). REQ vs capturas: el texto habla de validar ND; las evidencias muestran el modal FEV RIPS con mensaje de SPK_GENERAR_RIPS_JSON («No se encontró factura ni glosa para CNSFCT=…»), coherente con ministerio/SISPRO, no con el botón Aplicar de cartera. Causa: la grilla VWK_ESTADODIAN_FTRE (FTREComponent) expone el consecutivo de la nota en CNSFCT y no en CNSFNOT. ValidacionesFEVRipsComponent, para NC/ND, envía a FTR_COL · RIPS_JSON solo documento.CNSFNOT; al faltar, el parámetro CNSFCT llega vacío, SPK_GENERAR_RIPS_JSON no resuelve FNOT y devuelve el KO. Desde Notas DB/CR la fila FNOT incluye CNSFNOT y el mismo backend responde bien. Clasificación: defecto; impacto SQL No si se corrige el parámetro en FE.

5. Cambios propuestos

5.0 En palabras simples (negocio)

Hoy, si abre la validación FEV-RIPS de una nota débito desde Proceso DIAN, el sistema no le pasa el consecutivo de la nota al servidor y aparece un error técnico; desde Notas DB/CR sí lo pasa. Se propone que ambas pantallas envíen el mismo consecutivo (el de la nota) al validar ante el ministerio.

5.1 Detalle técnico — Frontend (Qrystalos2)

  1. Crear helper interno (o extender resolverCnsDocRips) que para tipoDocumento NC o ND devuelva documento.CNSFNOT || documento.CNSFCT (trim).
  2. Reemplazar usos que hoy leen solo CNSFNOT en: resolverParametrosRipsJsonDocumento, llamadas a ejecutarRipsJson, descarga ZIP, adjuntos XML/PDF, encolado async e identificadores de cola FEVRIPS.
  3. Probar camino B (NotiDian) y camino A (Notas DB/CR) con la misma ND.
  4. Opcional FTREComponent: al asignar fev.value en acción enviosYRespuestas, setear CNSFNOT cuando TIPODOC sea NOTACR o NOTADB.

5.2 Detalle técnico — SQL Server

No se requiere cambio en IXONLINE/SQL para este defecto. Referencia de comportamiento actual:

  • SPQ_FTR_COL · RIPS_JSON — ejecuta SPK_GENERAR_RIPS_JSON con CNSFCT y TIPODOC del JSON.
  • SPK_GENERAR_RIPS_JSON — para NOTADB/NOTACR busca FNOT donde FNOT.CNSFNOT = @CNSFCT; si @CNSFCT está vacío, devuelve el error observado en captura.

5.3 Detalle técnico — Backend (qrystalos.server)

Sin cambio de endpoints ni MODELO/METODO. El mismo POST JSON existente debe recibir CNSFCT poblado desde el frontend.

6. Qué tener en cuenta

  • Orden operativo: la nota debe estar aplicada y en estado DIAN compatible antes de FEV-RIPS (flujo cartera + XML DIAN).
  • VisorXMLsComponent deshabilita FEV RIPS para NC según ESTDIAN/DIAN; ND sigue reglas de notificación — no confundir con este bug de consecutivo.
  • Generación async (INICIAR_RIPS_JSON_JOB) usa el mismo CNSFCT+TIPODOC; la corrección debe aplicar también a ese hilo.
  • Riesgo de regresión bajo si el fallback CNSFCT solo aplica a NC/ND (facturas siguen usando CNSFCT de FTR).
