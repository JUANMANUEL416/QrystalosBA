FEVRIPS paquete Nueva EPS: XML 01 y RIPS en cero

Necesidad para el plan de trabajo. No es un dictamen de implementación.

COMITE DE ESTUDIOS MEDICOS

Para comité

1. Necesidad o problema

Alinear la factura electrónica (XML) y el RIPS JSON de atenciones por paquete Nueva EPS con las reglas del pagador y SISPRO: modalidad 01, total en el código de paquete, servicios y medicamentos del RIPS en $0, una autorización limpia por factura.

2. Análisis

Necesidad: Facturar y validar FEVRIPS de atenciones contratadas como paquete / canasta con Nueva EPS: el XML debe ir en modalidad 01 y el RIPS debe reportar los servicios y medicamentos del paquete en $0, con una autorización limpia.

Procesos: rips-json (JSON FEVRIPS) + hermano dian-xml (FEV). Ventanas: Validaciones FEVRIPS / FEVRIPS masivo; el XML sale al notificar DIAN (FACTE=2).

Paso 0 — ¿Ya existe? Defecto / desalineación normativa, no capacitación. El camino Generar/Validar RIPS y notificar DIAN existe. Hoy el JSON de masivas paquete CI sale sin servicios (RV601, caso 0100016449 / FV77759) y el XML no cumple las reglas Nueva EPS de modalidad 01 ni del código de paquete en el detalle.

Reglas Nueva EPS (diapositiva adjunta) + Anexo 1/2 SISPRO (Res. 2275 / 948):
1. XML MODALIDAD_PAGO = 01 (tabla modalidadPago).
2. Valor individual de servicios = 0; el total va en el XML bajo el código del paquete (ej. E8921001).
3. Ese código en cbc:Description y cac:StandardItemIdentification.
4. RIPS: códigos de servicios y medicamentos del paquete a $0 (RVC034 si se manda valor en no-evento).
5. numAutorizacion sin prefijo, guiones ni otros caracteres.
6. Una autorización por factura; extras por evento en otra FV.

Hoy (PREVERSION = 2.0.3 = última Cerrada):
- SPK_GENERAR_XML_DIAN no usa FTR.PAQUETE; vacío → 04. Excluye FTRD.PAQUETE IN (1,2): el código de paquete no entra al detalle; entra el cuerpo con valor.
- SPK_RIPS_JSON_FTR_MAS: UPDATE solo NOITEM=99 → servicios: {}. Ceros solo si PPT.PAQUETIZADO=1. @CEROS lee el nodo equivocado y no se usa. Autorización CI sin limpiar.
- SPK_RIPS_JSON_FTR_IND (evento individual): detecta paquete solo con el texto XML exacto (schemeID=01 + descripción + punto). Un CASE de vrUnitMedicamento (~L1522) pone 0 cuando no es paquete y valor cuando sí lo es (al revés de la norma). FNK_LIMPIATEXTO(...,'A-Z0-9-') deja guiones. Varios INSERT filtran HPRED.PAQUETE=0 y omiten componentes del paquete.
- Aval 0100016449 cubría solo el UPDATE de cuerpos en masivas (RV601). Esta SR amplia XML + MAS/CITPAQ + IND.

Clasificación: desarrollo SQL (XML + hojas MAS/CITPAQ/IND). Sin módulo nuevo ni cambio de contrato JSON FE.

3. Alcance

Incluye: SPK_GENERAR_XML_DIAN (MODALIDAD_PAGO 01 en contrato paquete Nueva EPS; InvoiceLine del código de paquete con el total; no enviar componentes con valor). SPK_RIPS_JSON_FTR_MAS: UPDATE de cuerpos, vrServicio/vrUnit=0 si XML 01/02/03, incluir consultas/procedimientos/medicamentos aunque valor=0, numAutorizacion limpia. Paridad SPK_RIPS_JSON_FTR_CITPAQ si plan NEDXC/NEDXS. SPK_RIPS_JSON_FTR_IND (factura individual / TIPOFAC<>M): detectar modalidad por schemeID (no por texto exacto), corregir CASE invertido de medicamentos, reportar componentes del paquete a $0, autorización sin extraños. Dato: CNT.MODALIDAD=01 o PPT.PAQUETIZADO=1.
No incluye: cambiar pantallas Vue ni contrato FE→SPQ_FTR_COL·RIPS_JSON. No forzar 01 por FTR.PAQUETE en todos los clientes (Facturación Evento sigue 04 si el contrato es evento). No PGP/capita/AUTPG salvo lectura de modalidad. No radicar CXC ni asiento.

4. Restricciones

Proyecto Comité de Estudios Médicos / Nueva EPS. Publicar solo los SP acordados en preversión. Si no hay línea cuerpo con cita, es dato, no el generador. Una autorización por FV; servicios extra van en factura evento. Contrastar PREVERSION vs 2.0.3 antes de codificar. No ejecutar los fragmentos desde BA.

5. Criterios

1) FV paquete Nueva EPS notificada DIAN (FACTE=2): XML MODALIDAD_PAGO schemeID=01.
2) El detalle XML tiene el código de paquete autorizado (Description + StandardItemIdentification) y el valor total; los componentes no van con plata.
3) Tras GENERAR=SI, FTRJSON: usuarios≥1 y al menos un ítem en servicios (consultas u otra lista); vrServicio/vrUnit=0.
4) numAutorizacion = autorización Nueva EPS sin prefijo ni extraños.
5) SISPRO: sin RV601 (servicios vacíos) ni RVC034 (valor en no-evento).
6) Factura masiva (MAS/CITPAQ) y factura individual (IND, TIPOFAC≠M) del mismo contrato paquete cumplen 3–5.
7) Factura con modalidad 04 conserva valores en el RIPS.
8) Validar antes: si PREVERSION ya cumple 1–6 en una FV de prueba, no hay desarrollo nuevo.

6. Recomendación

Llevar al plan como ajuste SQL de cuatro objetos: XML + MAS + CITPAQ + IND. Primero dato de contrato (CNT.MODALIDAD=01 o PAQUETIZADO). El aval 0100016449 (RV601) queda absorbido. Tras publicar, regenerar JSON (masiva e individual) y revalidar SISPRO en FV COMITE/Nueva EPS.

-- Especificación (no ejecutar desde BA).
-- Catálogo DESAIX: PREVERSION = 2.0.3, idéntica a última Cerrada (IDANT 2.0.2). El cambio NO está en canasta.
-- Objetos: SPK_GENERAR_XML_DIAN · SPK_RIPS_JSON_FTR_MAS · paridad SPK_RIPS_JSON_FTR_CITPAQ (NEDXC/NEDXS) · SPK_RIPS_JSON_FTR_IND.
-- Alcance: facturas paquete Nueva EPS / modalidad SISPRO 01. No forzar 01 por FTR.PAQUETE en todos los clientes.
-- Códigos modalidadPago: 01 paquete/canasta · 02 PGP · 03 capita · 04 evento.

-- ========== 1) XML · MODALIDAD_PAGO (SPK_GENERAR_XML_DIAN ~L308-349) ==========
-- BEFORE: CNT.MODALIDAD si 01-04; si no infiere PPT (capita/PGP/PAQUETIZADO); vacío → 04.
--         No mira FTR.PAQUETE. Hardcode NIT OFE 900986941 fuerza 04 aunque PAQUETIZADO=1.
-- AFTER (contrato Nueva EPS / CNT.MODALIDAD=01 o PPT.PAQUETIZADO=1):
--   Conservar CNT.MODALIDAD si ya es 01-04.
--   Si CNT vacío AND PPT.PAQUETIZADO=1 → 01 (salvo hardcode de otro OFE que no aplique a COMITE).
--   Dato preferido: llenar CNT.MODALIDAD='01' en el contrato Nueva EPS. No usar FTR.PAQUETE suelto.

-- Nodo correcto (ya existe ~L884 / ~L2396):
-- <Name>MODALIDAD_PAGO</Name>
-- <Value schemeName="salud_modalidad_pago.gc" schemeID="01">Pago individual por caso / Conjunto integral de atenciones / Paquete / Canasta</Value>
-- NO leer PaymentMeans salud_modalidades_pago.gc (ahí schemeID se mezcla con TIPOVENTA 1/2).

-- ========== 2) XML · detalle: código de paquete con el total (~L1695-1733, InvoiceLine ~L1960-1975) ==========
-- BEFORE: AND COALESCE(FTRD.PAQUETE,0) NOT IN (2, 1)
--         Description = FTRD.ANEXO; StandardItemIdentification = REFERENCIA del cuerpo (servicio con valor).
-- AFTER si modalidad XML = 01:
--   Incluir la línea FTRD.PAQUETE=1 (SER del paquete autorizado, ej. E8921001) con VLR_SERVICI = total del paquete.
--   No enviar en el XML los componentes PAQUETE IN (0,2) con valor (van al RIPS en 0).
--   cbc:Description y cac:StandardItemIdentification = código de paquete autorizado por Nueva EPS (SER.CODCUPS / IDALTERNA según PPT.IMPRIMEIDALTERNA).

-- ========== 3) RIPS MAS · UPDATE PROCEDENCIA (SPK_RIPS_JSON_FTR_MAS ~L472-479) ==========
-- BEFORE
IF COALESCE(@PAQUETE,0)=1 AND @PROCEDENCIA='CI'
BEGIN
    UPDATE FTRD SET PROCEDENCIA='CI'
    FROM FTR INNER JOIN FTRD ON FTR.N_FACTURA=FTRD.N_FACTURA
    WHERE FTRD.PROCEDENCIA IS NULL
      AND FTR.PROCEDENCIA='CI'
      AND FTRD.NOITEM=99
      AND FTR.N_FACTURA=@N_FACTURA
END

-- AFTER
IF COALESCE(@PAQUETE,0)=1 AND @PROCEDENCIA='CI'
BEGIN
    UPDATE FTRD SET PROCEDENCIA='CI'
    FROM FTR INNER JOIN FTRD ON FTR.N_FACTURA=FTRD.N_FACTURA
    WHERE FTR.N_FACTURA=@N_FACTURA
      AND FTR.PROCEDENCIA='CI'
      AND (FTRD.PROCEDENCIA IS NULL OR LTRIM(RTRIM(FTRD.PROCEDENCIA))='')
      AND (COALESCE(FTRD.PAQUETE,0) IN (0,3)
           OR COALESCE(FTRD.VR_TOTAL,0)>0
           OR COALESCE(FTRD.VLR_SERVICI,0)>0)
END
-- Repetir en SPK_RIPS_JSON_FTR_CITPAQ (~L175-184). No tratar PAQUETE=2 en cero como cuerpo facturable.

-- ========== 4) RIPS MAS · modalidad del XML y vrServicio (~L455-464, INSERT #CONSULTAS ~L672) ==========
-- BEFORE: @CEROS busca salud_modalidades_pago.gc schemeID=01 y NO SE USA.
--         vrServicio=0 solo si @PAQUETIZADO=1 AND @PAQUETE=1.
--         #USUARIOS/#CONSULTAS exigen VLR_SERVICI>0 si no hay PAQUETIZADO.
-- AFTER: leer el nodo correcto (como IND):
--   CHARINDEX('<Value schemeName="salud_modalidad_pago.gc" schemeID="01">', XML_AttachedDocument)
--   (también 02 y 03 para ceros).
-- Si schemeID IN ('01','02','03'):
--   vrServicio / vrUnitOS / vrUnitMedicamento = 0
--   incluir consultas, procedimientos y medicamentos del paquete AUNQUE VLR_SERVICI=0
--   NO cuadrar SUM(vrServicio) contra FTR.VALORSERVICIOS
-- Si schemeID='04': valor de FTRD (evento) + UPDATE de cuerpos.

-- ========== 5) RIPS · numAutorizacion Nueva EPS (consultas CI ~L659) ==========
-- BEFORE
numAutorizacion=COALESCE((SUBSTRING(CIT.NOAUTORIZACION,0,30)),'null')

-- AFTER
numAutorizacion=NULLIF(DBO.FNK_LIMPIATEXTO(COALESCE(CIT.NOAUTORIZACION,''),'A-Z0-9'),'')
-- Una autorización por factura; no mezclar servicios de evento (otra FV).

-- Validación (solo lectura, copia/preversión; no ejecutar desde BA):
-- 1) XML: schemeID 01 + una InvoiceLine con código paquete y total.
-- 2) JSON: $.rips.usuarios≥1 y al menos una lista de servicios con ítem; vrServicio=0.
-- 3) numAutorizacion sin prefijo/guiones.
-- 4) Regenerar GENERAR=SI; SISPRO sin RV601 ni RVC034.
-- 5) Factura evento (04) del mismo cliente no cambia.
-- 6) Factura individual (TIPOFAC<>M) misma regla vía SPK_RIPS_JSON_FTR_IND.
-- ========== 6) RIPS evento · SPK_RIPS_JSON_FTR_IND (PREVERSION 2.0.3 = liberada) ==========
-- Despacho: TIPOFAC<>M y no capita → esta hoja (factura individual / evento).
-- Ya lee el nodo correcto salud_modalidad_pago.gc. Falta alinear detección, ceros y autorización.

-- 6.1 Detección de paquete (~L410-418)
-- BEFORE: exige el texto EXACTO (incluye el punto final). Si TGEN.DESCRIPCION cambia, @PAQUETE queda 0.
AND CHARINDEX('<Value schemeName="salud_modalidad_pago.gc" schemeID="01">Pago individual por caso / Conjunto integral de atenciones / Paquete / Canasta.</Value>', XML_AttachedDocument) > 0

-- AFTER: por schemeID (01/02/03 = ceros; 04 = valor). No depender del texto.
AND (
      CHARINDEX('schemeName="salud_modalidad_pago.gc" schemeID="01"', XML_AttachedDocument) > 0
   OR CHARINDEX('schemeName="salud_modalidad_pago.gc" schemeID="02"', XML_AttachedDocument) > 0
   OR CHARINDEX('schemeName="salud_modalidad_pago.gc" schemeID="03"', XML_AttachedDocument) > 0
)
-- @PAQUETE=1 (ceros) si schemeID IN (01,02,03). Si 04, dejar 0 y reportar valor.

-- 6.2 vrUnit / vrServicio invertidos en un bloque de medicamentos (~L1522-1523)
-- BEFORE (comentario dice ceros en no-evento; el primer CASE hace lo contrario):
CASE WHEN COALESCE(@PAQUETE,0) = 0 THEN '0' ELSE CONVERT(VARCHAR,CONVERT(DECIMAL(14,2),HPRED.VALOR),20) END, -- vrUnit
CASE WHEN COALESCE(@PAQUETE,0) = 1 THEN '0' ELSE CONVERT(VARCHAR,CONVERT(DECIMAL(14,2),HPRED.VALOR*HPRED.CANTIDAD),20) END -- vrServicio

-- AFTER (ambos en 0 si paquete / modalidad 01-03):
CASE WHEN COALESCE(@PAQUETE,0) = 1 THEN '0' ELSE CONVERT(VARCHAR,CONVERT(DECIMAL(14,2),HPRED.VALOR),20) END,
CASE WHEN COALESCE(@PAQUETE,0) = 1 THEN '0' ELSE CONVERT(VARCHAR,CONVERT(DECIMAL(14,2),HPRED.VALOR*HPRED.CANTIDAD),20) END
-- Revisar el mismo patrón WHERE @PAQUETE=0 THEN 0 ELSE FTRD.VLR_SERVICI (~L1588).

-- 6.3 Incluir componentes del paquete en el JSON
-- Hoy varios INSERT filtran AND COALESCE(HPRED.PAQUETE,0)=0 (omite el detalle paquetizado)
-- y AND COALESCE(FTRD.PAQUETE,0) <> 2.
-- AFTER si @PAQUETE=1: reportar HPRED/FTRD de componentes (PAQUETE IN (0,2,3)) con vrServicio=0.
-- No omitir medicamentos del paquete (regla Nueva EPS).

-- 6.4 numAutorizacion (~28 usos de FNK_LIMPIATEXTO(...,'A-Z0-9-'))
-- BEFORE: deja el guion.
-- AFTER: FNK_LIMPIATEXTO(...,'A-Z0-9') — sin prefijo, guiones ni extraños.

-- Validación IND: FV TIPOFAC<>M, FACTE=2, XML 01, GENERAR=SI → servicios/medicamentos con valor 0,
-- autorización limpia, sin RV601/RVC034. Evento 04 del mismo cliente conserva valores.

8. Normativa y adjuntos

Nueva EPS — Reglas técnicas para facturar un paquete (diapositiva adjunta):
1) XML modalidad 01 (tabla SISPRO modalidadPago).
2) Valor individual de servicios en 0; total en el XML bajo el código del paquete (ej. E8921001).
3) Código de paquete autorizado en cbc:Description y cac:StandardItemIdentification.
4) RIPS JSON con códigos de servicios y medicamentos del paquete a $0.
5) Autorización Nueva EPS sin prefijo, guiones u otros caracteres.
6) Una autorización por factura; no mezclar extras (otra FV por evento).

SISPRO / Res. 2275 de 2023 y 948 de 2026 (Anexo 1): C17/P16/M18-M19/S11-S12 y RVC034: vrServicio mayor a cero solo en pago por evento; demás modalidades informar cero. Micrositio: https://www.sispro.gov.co/central-financiamiento/Pages/facturacion-electronica.aspx
