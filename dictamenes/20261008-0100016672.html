1. Requerimiento del cliente

Se solicita que el sistema permita colocar el impuesto y la base que corresponda cuando la cuenta contable está marcada como de IMPUESTO. Los campos deben reflejar el valor de la nota o del movimiento que se está aplicando (reclasificaciones manuales con retenciones, p. ej. honorarios al 11%). La respuesta previa que hablaba de «trasladar funcionalidad de Krystalos a Qrystalos» no responde al caso: el usuario necesita digitar base imponible y porcentaje en el comprobante manual, como en el sistema anterior.

2. Análisis del coordinador

Paso 0 — ¿Ya existe? No es capacitación. En Qrystalos2 el control detalle MCH ya incluye lógica de impuesto (lectura FIMPDV, autocalculo, variable USVGS PERMITIR_TODO), pero la interfaz de % Impuesto, Base y Autocalcular está oculta en comentarios HTML. El usuario solo captura Valor. Clasificación: hueco/regresión de interfaz en Movimiento Diario, no módulo nuevo. REQ vs captura: referencia legacy «Adicionando Nuevo Registro» — cuenta 23651510 (honorarios 11%), Base 650.000, Valor 71.500, autocalculo activo, proceso MANUAL. Misma necesidad en Qrystalos2 (/cont/mcp). Caminos del control inventariados: • Movimiento Diario → comprobante MANUAL no confirmado → Nuevo/Editar línea (MCHComponent) — camino principal del REQ. • Solo movimiento vs Cruce CxP/CxC (GENERA): el cruce trae VALOR del saldo; no reemplaza la captura manual de base/% en líneas impuesto. • Subir detalle desde Excel — fuera del alcance salvo que la plantilla ya traiga columnas de base/%. • Comprobantes errados → editar MCHE — hoy sin paridad de campos impuesto (opcional en desarrollo). • Tras guardar línea → RECALCULAR_TOTALES (sin cambio en este REQ). Causa: paridad incompleta del formulario MCH frente a legacy; IXONLINE/SQL · SPQ_MCH_COL · CRUDMCH ya persiste VALOR_PORCIMP y BASE_IMP. Veredicto releer .sql: METODOs CRUDMCH y RECALCULAR_TOTALES en estado leído en catálogo contabilidad; alcance cubierto por fichas. No se requiere bajar script adicional para implementar (validar en PREVERSION que CRUDMCH del cliente persiste ambos campos).

Criterios de aceptación

  1. En /cont/mcp, línea MCH con CUE.IMPUESTO=1: formulario muestra % Impuesto, Base y (si PERMITIR_TODO=SI) Autocalcular.
  2. Al elegir cuenta impuesto, % desde FIMPDV vigente; usuario digita Base del movimiento aplicado (ej. 650.000 × 11% → 71.500).
  3. Autocalcular: VALOR = redondeo(Base × % / 100); respeta tope FIMPDV.VALOR_INICIAL cuando PERMITIR_TODO≠SI.
  4. CRUDMCH persiste y relee VALOR_PORCIMP y BASE_IMP.
  5. Cuenta no impuesto: campos ocultos y valores limpiados.
  6. Validación al guardar: Base obligatoria > 0 para cuenta impuesto.
  7. Regresión: confirmación masiva, liquidación impuestos, comprobantes MANUAL sin regresión.

Alcance y restricciones

Alcance: Control detalle MCH en Movimiento Diario; reactivación UI y reglas en MCHComponent; lecturas FIMPDV/NTZ/CUE existentes; persistencia CRUDMCH.

Fuera de alcance: SPK_NC_* de Otros Módulos, liquidación SPQ_CONTA_LIQIMP, cambios en plan CUE_COL, rediseño de plantilla Excel; debate genérico Krystalos→Qrystalos.

5. Cambios propuestos

5.0 En palabras simples (negocio)

Hoy, en Movimiento Diario, si elige una cuenta marcada como impuesto no puede ver ni editar el porcentaje ni la base imponible; solo el valor total. Se propone mostrar de nuevo esos campos (como en el sistema anterior), calcular el valor del impuesto a partir de base y porcentaje cuando corresponda, y guardarlos en el movimiento para informes y liquidación de impuestos.

5.1 Detalle técnico — Frontend (Qrystalos2)

  • MCHComponent.vue — Reactivar bloque comentado «Ocultos por ahora» (% Impuesto, Base, checkbox Autocalcular) con v-if="mostrarImpuesto".
  • Restaurar valorImpuestoReadonly para bloquear Valor cuando autocalculo aplica y PERMITIR_TODO≠SI (según lógica comentada).
  • Descomentar validación al guardar: Base obligatoria > 0 si cuenta impuesto.
  • Mantener cargarFimpdvCuenta al seleccionar cuenta (VALOR_PORCIMP, REFERENCIA1-3 impuesto, tope VALOR_INICIAL).
  • Mantener recalcularValorImpuesto y USVGS PERMITIR_TODO en onMounted.
  • Opcional: replicar patrón en MCHEComponent para edición en comprobantes errados.

5.2 Detalle técnico — SQL Server

No hay cambio de objetos IXONLINE/SQL en el alcance acordado. SPQ_MCH_COL · CRUDMCH ya recibe y persiste VALOR_PORCIMP y BASE_IMP en INSERT/EDITAR. Desarrollador: confirmar versión desplegada en PREVERSION del cliente antes de cerrar ticket.

5.3 Detalle técnico — Backend (qrystalos.server)

Sin cambio: mismo contrato JSON { MODELO: "MCH_COL", METODO: "CRUDMCH", PARAMETROS: { REGISTRO } }.

6. Qué tener en cuenta

  • Parametrización FIMPDV por cuenta y vigencia: sin fila vigente el % puede quedar vacío; usuario debe poder completar según PERMITIR_TODO.
  • Referencias REFERENCIA1-3 se usan para identificador impuesto/clase/ítem al cargar FIMPDV; no confundir con referencias de cruce CxP/CxC.
  • Liquidación de impuestos excluye movimientos sin base; capturar BASE_IMP evita exclusiones silenciosas en certificados.
  • Rama sugerida: feature/CMAICA197.

7. Pruebas del desarrollador

  • Lint/build Qrystalos2 en rama del REQ.
  • Cuenta CUE.IMPUESTO=1 con FIMPDV vigente: flujo insertar y editar línea; Base 650.000, 11%, autocalculo → Valor 71500.
