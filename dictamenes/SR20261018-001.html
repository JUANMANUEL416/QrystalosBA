FEV-RIPS: reportar todo lo facturado y no ocultar el fallo

Necesidad para el plan de trabajo. No es un dictamen de implementación.

SR20261018-001
rips-json
2026-10-18
Para comité
Alta
SPQ_FTR_COL

1. Necesidad o problema

Al generar el RIPS JSON de una factura electrónica, de una nota o de un ajuste, deben salir todos los servicios y las estancias que ya están en la factura, con el código y el valor que el Ministerio espera. El tipo de usuario y el CUM del medicamento deben salir del evento facturado, no de un padrón distinto. Si la generación falla, el usuario tiene que verlo: el trabajo no puede quedar como terminado. Un ajuste de cápita que no es PGP también debe volver a armar el JSON.

2. Análisis

Clasificación: defecto. No es capacitación ni hueco de pantalla: el camino existe (Administrativo → Facturación → generar RIPS JSON / FEV) y pierde datos o miente el estado. Contrastado con IXONLINE/SQL PREVERSION 2.0.10 (idéntica a la liberada 2.0.10; IDANT 2.0.9). Confirmados 1. INNER JOIN RIPS_CP por SER.CODIGORIPS: sin homologar, el ítem no entra. SPK_RIPS_JSON_FTR_IND :983 y el resto de hojas. 2. Masiva y capitación masiva exigen DATEDIFF(HOUR, ingreso, alta) ≤ 48 en urgencias y hospitalización: omiten estancias de más de 48 h. SPK_RIPS_JSON_FTR_MAS :1389/:1421; SPK_RIPS_JSON_FTR_CAPMASI :862/:893. 3. CAPMASI hace UPDATE HADM.FECHA si el alta es anterior al ingreso :835-844. 4. IND UPDATE de CUM: el WHERE de :1645 y :1649 mezcla AND/OR sin paréntesis. El SET ya usa COALESCE (:1641). En AT de cita, vrUnitOS y vrServicio ambos = FTRD.VLR_SERVICI con cantidadOS = CIT.CANTIDADC :1147. 5. SPQ_FTR_COL · EJECUTAR_RIPS_JSON_ASYNC marca COMPLETADO aunque GENERAR devuelva KO por result set, no por RAISERROR :4277-4289. SPK_GENERAR_RIPS_JSON no regenera AJUSTE de cápita (TIPOCAP < 4 ni TIPOCAP = 4) :190-199. Descartados (no pedirlos) - Lista CITPAQ distinta: DESAIX :469 es NEDXC, NEDXS, NCDXPS, NSDXPS. - SPK_RIPS_PREVALIDAR_FTR_CAPI no existe. - Valor invertido en paquetizados: ya corregido (SR20260922-001); el fallo vivo es AT :1147. Nota. SPK_RIPS_JSON_NOTAAJUSTE_MAS y NOTAAJUSTE_PGP no se llaman desde FTR_COL (quedan después del RETURN de AJUSTE). Tienen el mismo filtro de 48 h, pero no se pide corregirlos hasta reactivar el camino. Finalidad, causa y modalidad no son un fallo único: cada hoja tiene su default. Unificarlos sería otro alcance.

3. Alcance

Generación del RIPS JSON (evento, masiva, cápita, capitación masiva, PGP, programa, paquete, ajuste y nota) y el trabajo en cola de FTR_COL. Incluye: no silenciar ítems sin homologar; reportar estancias de más de 48 h en masiva y capitación masiva; quitar el UPDATE de HADM del generador; corregir el WHERE del CUM y los valores AT de cita en evento; tomar tipo de usuario del evento; unificar la cadena CUM; marcar error el trabajo si GENERAR falla; regenerar el JSON del ajuste de cápita que no es PGP.

4. Restricciones

No incluye reescribir las hojas a INSERT SELECT / FOR JSON PATH ni dejar de llamar FNK_LIMPIATEXTO por fila (mejora de velocidad; otro paquete si el comité lo pide). No cambia el XML DIAN, el RIPS plano TXT, ni radicar CXC. No rehace JSON ya enviados con CUV. No unifica los defaults de finalidad, causa y modalidad entre hojas. SPK_RIPS_JSON_NOTAAJUSTE_MAS y NOTAAJUSTE_PGP: SP sin uso desde FTR_COL. Corregir solo si se reactivan.

5. Criterios

1. Un servicio facturado sin código RIPS homologado no desaparece en silencio: o entra al JSON o el usuario ve cuáles faltaron. 2. Una urgencia u hospitalización de más de 48 horas en factura masiva o capitación masiva sí se reporta. 3. Generar el JSON de capitación masiva no cambia HADM.FECHA. 4. En evento, el UPDATE de CUM solo toca medicamentos (MEDICAMENTOS=1) y códigos vacíos o sin guion: el AND/OR del WHERE va entre paréntesis. 5. En otros servicios de cita (AT), el valor unitario es el del ítem dividido por la cantidad y el valor del servicio es el del ítem. 6. Si la generación devuelve error, el trabajo en cola queda en error y el usuario lo ve; no queda Completado. 7. Un ajuste de cápita que no es PGP vuelve a armar el JSON de esa nota. 8. El tipo de usuario del JSON sale del evento (admisión, autorización de programa o afiliado, según la hoja), no de un padrón distinto al facturado. 9. El CUM del medicamento sigue una sola cadena acordada; si todo está vacío, el JSON no inventa un código. 10. Una factura evento o PGP sin estos casos sigue generando como hoy.

6. Recomendación

Llevar a comité. Es defecto sobre el proceso rips-json ya documentado: el camino existe y falla. Viable en IXONLINE/SQL, sin pantalla nueva. Orden sugerido: 1) LEFT JOIN RIPS_CP con rechazo explícito en las hojas vivas; 2) quitar el filtro de 48 h en MAS y CAPMASI; 3) sacar el UPDATE HADM de CAPMASI; 4) paréntesis del WHERE de CUM y valores AT en IND; 5) tipo de usuario del evento; 6) una cadena CUM; 7) el async solo marca COMPLETADO si GENERAR no trajo KO; 8) el despachador regenera el AJUSTE de cápita no-PGP. La reescritura por velocidad (cursores, FNK_LIMPIATEXTO) se deja para un segundo paquete.

9. Sugerencia de código SQL

Especificación para el comité y el desarrollador. No ejecutar desde BA. Contrastar PREVERSION vs última Cerrada antes de implementar.

IXONLINE/SQL. Especificación; no ejecutar desde BA.

1) Hojas vivas SPK_RIPS_JSON_FTR_* / AJUSTE_* / NDBCR_IND:
   Hoy: INNER JOIN RIPS_CP ON SER.CODIGORIPS = RIPS_CP.IDCONCEPTORIPS
   Esperado: LEFT JOIN RIPS_CP y, si CODIGORIPS queda vacío, no silenciar el ítem
   (rechazo con mensaje o bitácora de no homologados).

2) SPK_RIPS_JSON_FTR_MAS :1389/:1421 y SPK_RIPS_JSON_FTR_CAPMASI :862/:893:
   Hoy: AND DATEDIFF(HOUR, HADM.FECHA, HADM.FECHAALTAMED) <= 48
   Esperado: quitar esa condición. Reportar la estancia con su duración real.
   Nota: NOTAAJUSTE_MAS tiene el mismo filtro (:1048/:1080) pero no se llama desde FTR_COL.
         Corregir solo si se reactiva.

3) SPK_RIPS_JSON_FTR_CAPMASI :835-844:
   Hoy: UPDATE HADM SET FECHA = ... si DATEDIFF hora/minuto alta-ingreso < 0
   Esperado: no actualizar HADM desde el generador del JSON.

4) SPK_RIPS_JSON_FTR_IND :1645 y :1649 — WHERE, no el SET.
   Hoy:
     WHERE SER.MEDICAMENTOS=1 AND ISNULL(A.codTecnologiaSalud,'')=''
        OR ISNULL(A.codTecnologiaSalud,'') NOT LIKE '%-%'
     (AND ata primero: todo código sin guion entra, sea o no medicamento)
   Esperado:
     WHERE SER.MEDICAMENTOS=1
       AND (ISNULL(A.codTecnologiaSalud,'')=''
            OR ISNULL(A.codTecnologiaSalud,'') NOT LIKE '%-%')
   El SET :1641 ya es COALESCE(NULLIF(IUM,''), NULLIF(CODCUM,''), NULLIF(SER.CODCUM,'')). No tocarlo.

5) SPK_RIPS_JSON_FTR_IND AT :1147:
   Hoy: vrUnitOS = vrServicio = FTRD.VLR_SERVICI, cantidadOS = CIT.CANTIDADC
   Esperado: vrServicio = VLR_SERVICI; vrUnitOS = VLR_SERVICI / CANTIDADC cuando la cantidad > 0.

6) SPQ_FTR_COL · EJECUTAR_RIPS_JSON_ASYNC :4277-4289:
   Hoy: COMPLETADO si no hay excepción SQL
   Esperado: si GENERAR devuelve KO (result set), ESTADO = ERROR con el mensaje; no COMPLETADO.

7) SPK_GENERAR_RIPS_JSON :190-199:
   Hoy: AJUSTE cápita TIPOCAP<4 y TIPOCAP=4 no regeneran y RETURN
   Esperado: regenerar el JSON de esa nota (hoja del documento origen).

13. Hoy frente a lo propuesto

Hoy

El ítem sin homologar no entra. Masiva y capitación masiva omiten estancias de más de 48 h. CAPMASI puede cambiar la fecha de la admisión. El WHERE del CUM en IND mezcla AND/OR. El job queda Completado si GENERAR falló. El ajuste de cápita no regenera. El tipo de usuario y el CUM no son los mismos en todas las hojas.

Propuesto

Todo lo facturado entra o se informa. Las estancias largas se reportan. El generador no toca HADM. El WHERE del CUM solo aplica a medicamentos. El trabajo muestra el error. El ajuste de cápita vuelve a armar el JSON. Tipo de usuario del evento y una cadena CUM.
