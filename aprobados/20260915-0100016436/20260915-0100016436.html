1. Requerimiento del cliente

Validación de tipo de afiliado al enviar facturas a la DIAN. Se solicita que el sistema no valide el tipo de afiliado cuando la factura sea para un particular al momento de enviar la información a la DIAN. 1. Generar una factura para un particular. 2. Intentar enviar la factura a la DIAN.

Criterios de aceptación

1. Factura particular (misma regla que FTRFE_COL · VALIDAFTR: plan en USVGS IDPLANPART%, procedencia CAJA o tercero con ENVIODICAJA=1): al encolar y generar XML DIAN no se bloquea por tipo de usuario / tipo de afiliado (código TU_INVALIDO). 2. Factura EPS o plan no particular: se mantiene la validación cruzada actual. 3. NOTI_DIAN / FE_ENCOLAR conservan sus reglas (fecha del día, capita/PGP con FTRDC, resolución). 4. Prueba en preversión: particular con paciente sin TIPOUSUARIO coherente con cobertura EPS → FACTE avanza (o al menos XML sin RAISERROR de tipo usuario). 5. Regresión: factura a EPS con tipo de usuario inválido para la cobertura sigue fallando como hoy.

2. Análisis del coordinador

Proceso conocimiento: dian-xml (hermano de facturacion). Paso 0 — Clasificación: defecto de regla (no capacitación, no botón nuevo). El usuario usa el circuito estándar: Facturación → Encolar DIAN (NOTI_DIAN) o pestaña Proceso DIAN. El encolado no valida tipo de afiliado. El bloqueo ocurre cuando el facturador arma el XML. SQL leído hoy desde DESAIX.SQLIX (servidor 9 / DESAIX): • PREVERSION = 2.0.0 = 1.8.32 para SPK_GENERAR_XML_DIAN y SPK_VALID_CRUZADA_FEV (mismos hashes). El arreglo no está en la canasta abierta. • Guard clause en SPK_GENERAR_XML_DIAN: solo omite SPK_VALID_CRUZADA_FEV si procedencia CAJA/INVENTARIO o IDPLAN está en IDPLANPART%. • VALIDAFTR marca particular también si TER.ENVIODICAJA=1. Ese camino no está en el guard: una FV «particular» por tercero de caja, con plan que no está en IDPLANPART%, sí entra a la cruzada. • SPK_VALID_CRUZADA_FEV exige TIPOUSUARIO (AFI o HADM.TIPOAFILIADO) vigente en RIPS_VALID_COB_TU para la cobertura del plan (PLN.TIPOVOLUNTARIO). Mensaje: «El tipo de usuario X no es válido para la cobertura Y» (TU_INVALIDO), prefijado «Documento detenido en validación FEV/RIPS». Contabilidad: no aplica.

Validar antes de desarrollar

Si FACTE=2 sin error de tipo usuario, no desarrollar. Si RAISERROR TU_INVALIDO / «Documento detenido en validación FEV/RIPS», aplicar este dictamen. Anotar N_FACTURA, IDPLAN, ENVIODICAJA y si el plan está en IDPLANPART%.
  • Reproducir en rama bugfix/CLIVID33 o copia Clinivida.

5. Cambios propuestos

5.0 En palabras simples (negocio)

Hoy, al enviar a la DIAN una factura de un paciente particular, el sistema a veces exige el mismo tipo de afiliado que en una factura a EPS y el envío se detiene. Se propone que, si la factura es de particular (como ya la reconoce el sistema en otros pasos), no se haga esa comprobación. Las facturas a aseguradoras siguen controladas.

5.1 Detalle técnico — Frontend (Qrystalos2)

Sin cambio. No hay botón ni mensaje nuevo. Opcional (fuera de alcance): mostrar en pantalla si el plan particular no está en IDPLANPART%.

5.2 Detalle técnico — SQL Server

Punto de partida: sql/SPK_GENERAR_XML_DIAN.sql (PREVERSION). Bloque (~354–364): Hoy: IF afiliado y tercero y FV AND procedencia NOT IN (CAJA, INVENTARIO) AND IDPLAN NOT IN (USVGS IDPLANPART%) EXEC SPK_VALID_CRUZADA_FEV … Propuesto (opción A): Añadir exclusión si el tercero de la FTR tiene ENVIODICAJA=1 (JOIN TER, mismo predicado que VALIDAFTR). Mantener CAJA e IDPLANPART%. No relajar SPK_VALID_CRUZADA_FEV para EPS. No ejecutar el SP desde BA. Configuración: revisar USVGS IDPLANPART% en Clinivida; si el plan particular no está, incluirlo además del cambio de código (doble seguridad).

5.3 Detalle técnico — Backend (qrystalos.server)

Sin cambio de API. El servicio facturador sigue llamando SPK_GENERAR_XML_DIAN. Publicar el SP en el ambiente del cliente (qrystalosServer no configurado en BA).
