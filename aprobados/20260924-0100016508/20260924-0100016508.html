1. Requerimiento del cliente

Al generar el RIPS JSON de una nota de ajuste de evento, el sistema debe encontrar la factura tanto si le pasan el consecutivo de la factura como el de la glosa.

Criterios de aceptación

1) Con factura de evento no cápita, FACTE=2 y al menos una glosa en FGLO: generar RIPS JSON (TIPODOC=AJUSTE, GENERAR=SI) con parámetro CNSFCT igual al consecutivo de la factura (FTR.CNSFCT) debe completar el JSON sin «No se encontró la procedencia de la factura» ni fallo por UBL nulo. 2) Misma factura: generar con parámetro igual a FGLO.CNSGLO de cualquiera de sus glosas debe resolver la misma FTR y el mismo N_FACTURA. 3) Factura de evento sin glosas: comportamiento igual al actual (búsqueda por CNSFCT). 4) Facturas cápita/PGP y notas crédito/débito: sin cambio (no pasan por SPK_RIPS_JSON_AJUSTE_IND). 5) Tras publicar el SP, una nota de ajuste que ya generaba bien por CNSGLO sigue generando el mismo sobre {rips, xmlFevFile}.

Alcance y restricciones

Alcance: Un solo objeto SQL: DBO.SPK_RIPS_JSON_AJUSTE_IND — bloque inicial que asigna procedencia, admisión, CNSFCT, N_FACTURA y copago desde FTR. Proceso rips-json, control Generar RIPS JSON en nota de ajuste de evento (Validaciones FEV-RIPS / FEV-RIPS masivo, TIPODOC AJUSTE). Restricciones: Publicar solo CREATE OR ALTER de SPK_RIPS_JSON_AJUSTE_IND (no crear SPK_RIPS_JSON_AJUSTE_IND1 en servidor). Confirmar en PREVERSION que el SELECT sigue siendo el LEFT JOIN FGLO antes de aplicar. Si un mismo valor pudiera ser CNSFCT de una factura y CNSGLO de otra, evaluar ORDER BY (prioridad factura) — no incluido en la copia de especificación actual.

2. Análisis del coordinador

5. Cambios propuestos

5.0 En palabras simples (negocio)

Hoy, al generar el JSON de una nota de ajuste sobre una factura que ya tiene glosas, si el sistema recibe el consecutivo de la factura no la encuentra y se detiene. Se corrige la consulta inicial del procedimiento para que acepte tanto el consecutivo de la factura como el de la glosa, sin duplicar la factura cuando hay varias glosas.

5.2.1 Fragmentos SQL (especificación) — no ejecutar desde BA.

-- BEFORE (sql_refe/20260914, ~líneas 254-258)
SELECT @PROCEDENCIA=FTR.PROCEDENCIA, @NOADMISION=FTR.NOREFERENCIA, @IDSEDE=IDSEDE
     , @VALORCOPAGO=CASE WHEN COALESCE(CAPITADA,0)=0 THEN COALESCE(VALORCOPAGO,0)
           ELSE CASE WHEN COALESCE(COPAPROPIO,0)=1 THEN COALESCE(CP_VLR_COPAGOS,0)
                ELSE COALESCE(VALORCOPAGO,0) END END
     , @CNSFCT=CNSFCT, @IDPLAN=FTR.IDPLAN, @N_FACTURA=FTR.N_FACTURA
FROM FTR LEFT JOIN FGLO ON FTR.N_FACTURA=FGLO.N_FACTURA
WHERE @CNSGLO = CASE WHEN FGLO.CNSGLO IS NULL THEN FTR.CNSFCT ELSE FGLO.CNSGLO END;

-- AFTER (publicar en SPK_RIPS_JSON_AJUSTE_IND)
SELECT TOP 1 @PROCEDENCIA=FTR.PROCEDENCIA, @NOADMISION=FTR.NOREFERENCIA, @IDSEDE=IDSEDE
     , @VALORCOPAGO=CASE WHEN COALESCE(CAPITADA,0)=0 THEN COALESCE(VALORCOPAGO,0)
           ELSE CASE WHEN COALESCE(COPAPROPIO,0)=1 THEN COALESCE(CP_VLR_COPAGOS,0)
                ELSE COALESCE(VALORCOPAGO,0) END END
     , @CNSFCT=CNSFCT, @IDPLAN=FTR.IDPLAN, @N_FACTURA=FTR.N_FACTURA
FROM FTR
WHERE FTR.CNSFCT = @CNSGLO
   OR EXISTS (
        SELECT 1 FROM FGLO
        WHERE FGLO.N_FACTURA = FTR.N_FACTURA
          AND FGLO.CNSGLO = @CNSGLO
      );

-- Validación (solo lectura)
SELECT FTR.CNSFCT, FTR.N_FACTURA, FTR.PROCEDENCIA, FTR.CAPITADA, FTR.FACTE
FROM FTR
WHERE FTR.CNSFCT = @CNSGLO
   OR EXISTS (
        SELECT 1 FROM FGLO
        WHERE FGLO.N_FACTURA = FTR.N_FACTURA AND FGLO.CNSGLO = @CNSGLO
      );

6. Qué tener en cuenta

  • Glosa con valor aceptado > 0: el FE orienta a nota crédito, no NA (esGlosaAceptadaNoAplicaNa) — fuera de este fix.
  • AJUSTE cápita/PGP usa otras hojas (SPK_RIPS_JSON_AJUSTE_PGP, etc.).
  • TOP 1 sin ORDER BY: riesgo teórico si un valor colisionara entre CNSFCT y CNSGLO de otra factura — documentado en control de cambios.
  • Rollback: republicar cuerpo de sql_refe/20260914/SPK_RIPS_JSON_AJUSTE_IND.sql.
