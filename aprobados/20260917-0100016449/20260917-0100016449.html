1. Requerimiento del cliente

se requiere que se corrija los where cuando son paquetes debido a que no esta enviando los servicios paquetizados o envían valores en cero

Criterios de aceptación

1) Factura de prueba masiva de citas paquete: FTR.TIPOFAC=M, FTR.PROCEDENCIA=CI, FTR.PAQUETE=1, FACTE=2 (notificada DIAN), con al menos una línea FTRD «cuerpo» (PAQUETE IN (0,3) o VR_TOTAL/VLR_SERVICI > 0) vinculada a CIT vía NOADMISION. 2) Tras GENERAR=SI (Validar ahora / FEV RIPS o FEVRIPS masivo), el JSON persistido en FTRJSON debe tener $.rips.usuarios con al menos un usuario y, en ese usuario, al menos un ítem en servicios (consultas u otra lista exigida por el caso), con valor de servicio coherente con FTRD (no objeto servicios vacío ni totales en cero cuando la factura tiene valor). 3) Validación externa SISPRO sobre ese JSON: no rechazo RV601 por «servicios sin ítems» ni RVG01 por usuarios vacíos en el escenario paquete CI descrito. 4) Regresión: factura masiva M sin paquete (FTR.PAQUETE≠1 o sin bandera paquete) conserva el mismo JSON que antes; factura individual (TIPOFAC≠M) no alterada. 5) Si el plan es NEDXC/NEDXS (hoja CITPAQ), repetir criterios 1–3 por esa ruta de despacho.

Proceso: rips-json (control Generar RIPS JSON). Ventanas: ValidacionesFEVRipsComponent / FEVRIPSMasivoPage (useRipsJsonAsync) y pestaña FEV RIPS en factura (Validar ahora, Editar JSON, validación SISPRO). Paso 0 — Clasificación: defecto SQL en hoja masiva paquete CI (no capacitación ni hueco de pantalla). Evidencia FV77759 (CNS 0600077871): usuario en JSON pero servicios vacíos; SISPRO RV601; editor «Este usuario no tiene servicios registrados». El UPDATE previo a #USUARIOS no marca esas líneas como CI; los INSERT de consultas exigen PROCEDENCIA='CI' y cuerpo con valor → JSON incompleto. Veredicto releer .sql hoy: fichas SPQ_FTR_COL · RIPS_JSON, SPK_GENERAR_RIPS_JSON, SPK_RIPS_JSON_FTR_MAS y SPK_RIPS_JSON_FTR_CITPAQ están leídas en conocimiento/rips-json/sps.json para el flujo; el diff del UPDATE paquete debe contrastarse con PREVERSION y con la nota técnica del caso (sql_refe/20260914 aún filtra NOITEM=99). 5. Cambios propuestos

5.0 En palabras simples (negocio)

En facturas masivas de citas marcadas como paquete, el sistema debe tomar la línea de detalle donde está el dinero (no solo la cabecera del paquete) para armar los servicios del RIPS; hoy ese detalle queda fuera por un filtro incorrecto y el JSON sale sin consultas o con valores en cero.

IF COALESCE(@PAQUETE,0)=1 AND @PROCEDENCIA='CI'
BEGIN
    UPDATE FTRD SET PROCEDENCIA='CI'
    FROM FTR INNER JOIN FTRD ON FTR.N_FACTURA=FTRD.N_FACTURA
    WHERE FTRD.PROCEDENCIA IS NULL
      AND FTR.PROCEDENCIA='CI'

END

Propuesto — UPDATE alineado a cuerpos facturables (misma lógica que INSERT #USUARIOS)

IF COALESCE(@PAQUETE,0)=1 AND @PROCEDENCIA='CI'
BEGIN
    UPDATE FTRD SET PROCEDENCIA='CI'
    FROM FTR INNER JOIN FTRD ON FTR.N_FACTURA=FTRD.N_FACTURA
    WHERE FTR.N_FACTURA=@N_FACTURA
      AND FTR.PROCEDENCIA='CI'
      AND (FTRD.PROCEDENCIA IS NULL OR LTRIM(RTRIM(FTRD.PROCEDENCIA))='')
      AND (
            COALESCE(FTRD.PAQUETE,0) IN (0,3)
         OR COALESCE(FTRD.VR_TOTAL,0) > 0
         OR COALESCE(FTRD.VLR_SERVICI,0) > 0
      )
      /* No tratar PAQUETE=2 en cero como cuerpo (alcance REQ) */
END

SELECT CNSFCT, N_FACTURA, TIPOFAC, PROCEDENCIA, PAQUETE, FACTE, IDPLAN
FROM FTR
WHERE CNSFCT = @CNSFCT;

SELECT N_CUOTA, REFERENCIA, NOITEM, PAQUETE, PROCEDENCIA, VLR_SERVICI, VR_TOTAL, NOADMISION
FROM FTRD
WHERE CNSFTR = @CNSFCT
ORDER BY N_CUOTA;

SELECT
  JSON_VALUE(JSON_ENVIO, '$.rips.numFactura') AS NUMFACT,
  (SELECT COUNT(*) FROM OPENJSON(JSON_ENVIO, '$.rips.usuarios')) AS CANT_USUARIOS,
  (SELECT COUNT(*)
   FROM OPENJSON(JSON_ENVIO, '$.rips.usuarios') U
   CROSS APPLY OPENJSON(U.value, '$.servicios.consultas')) AS CANT_CONSULTAS
FROM FTRJSON
WHERE CNSFCT = @CNSFCT;
