1. Requerimiento del cliente

Corrección de validación de modalidad en el modal de creación de factura Se requiere ajustar la validación del campo 'Modalidad' en el modal de creación de factura. Actualmente, se genera un mensaje de error confuso cuando el usuario ingresa la modalidad 'PGP', ya que el sistema exige un mínimo de 5 caracteres. Se debe reducir este mínimo a 3 caracteres y actualizar el mensaje de error para que sea claro y específico. 1. El campo 'Modalidad' acepta un mínimo de 3 caracteres. 2. El mensaje de error se actualiza a: 'La modalidad debe tener al menos 3 caracteres.' cuando se ingresa menos de 3 caracteres. 3. No se generan errores al ingresar modalidades válidas de 3 caracteres o más.

Criterios de aceptación

1. En Administrativo → Facturación → pestaña Facturas → Nueva Factura, con plan PGP o capitado (bloque «Información de Capitación/PGP» visible), el campo Modalidad acepta valores de 3 caracteres o más (ej. «PGP»). 2. Si Modalidad tiene menos de 3 caracteres, el sistema muestra: «La modalidad debe tener al menos 3 caracteres.» y no guarda la cabecera. 3. Con Modalidad «PGP» u otra de longitud ≥3, y el resto de datos válidos (observación ≥15 caracteres en Colombia, convenio según SISPRO, etc.), el guardado vía CREARFTR concluye sin error por modalidad. 4. Facturas por evento (sin cápita/PGP) no exigen Modalidad; el cambio no altera ese flujo.

2. Análisis del coordinador

REQ 0100013651 (tipo Performance/bug): al crear factura manual con contrato PGP, «PGP» (3 letras) es rechazado por validación que exige 5 caracteres y mensaje poco claro. Paso 0 — ¿ya existe?: No es capacitación ni hueco de módulo. El camino correcto es Nueva Factura → plan PGP/capitado → Información Capitación/PGP → guardar (CREARFTR). No hay otro botón alterno para «modalidad corta». Clasificación: defecto de validación UX en FE (históricamente umbral 5 en código legacy; en Qrystalos2 actual FTRComponent.vue valida length < 3 pero el notify sigue siendo genérico «Debe Ingresar la Modalidad», incumpliendo CA del REQ). Evidencia Qrystalos2: validaFTR() aplica solo si esCapitaPgp (CAPITADA o capipgpeve 1/2); String(model.MODALIDAD).length < 3 bloquea guardado. SPQ_FTR_COL CREARFTR (conocimiento/facturacion/sps.json, leído) no lista validación de longitud de CP_MODALIDAD. Confusión posible con Convenio (trim.length < 4, mensaje SISPRO), no con Modalidad. Caminos del gate inventariados: Nueva Factura / Editar cabecera mismo modal; TIPOCAP masiva (4) oculta bloque capita; por evento no pide Modalidad; Perú usa FTRPeComponent (validación MODALIDAD comentada — no mezclar). SQL del día: CREARFTR está leído en sps.json y el alcance no sale de validaciones no documentadas en servidor → no se exige SPQ_FTR_COL.sql en sql/ para este dictamen. Releer solo si en test Wayuu aparece rechazo backend al guardar «PGP».
